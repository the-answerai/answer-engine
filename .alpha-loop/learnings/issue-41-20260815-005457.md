# Issue #41 — isolate stable and staging local channels

## Identity must be explicit end to end

Resource separation is incomplete if a consumer can silently infer the stable
channel. The server health contract, CLI status, installer verification, and web
identity all need to carry and validate the selected channel. In particular, the
web client must fail closed when health omits or misstates channel identity so a
staging runtime cannot be rendered with stable branding.

## Compatibility includes resource names

Adopting an existing stable installation without mutation requires preserving
more than its home and ports. Compose project and generated volume names are
part of the durable storage identity. The stable profile therefore retains the
legacy project and effective volume names, while adoption only records ownership
metadata and the explicit channel marker.

## Collision checks belong before service execution

Safe defaults do not protect custom configuration. Canonical path and symlink
resolution, ports, projects, databases, volumes, service identifiers, credential
files, and secret fingerprints must be compared before any service-capable
action. Destructive lifecycle actions additionally require a matching ownership
marker, and staging history sync requires both persisted opt-in and explicit
confirmation.

## Verification lesson

Isolation needs both structural and behavioral proof: regression tests for every
known collision class, fixture-backed mutation checks, concurrent channel-aware
status contracts, and live desktop/mobile staging identity checks. Runtime
verification must use isolated fixture ports and never operate the user's stable
Compose project.
